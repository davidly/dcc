This document is a **self-contained execution spec** for continuing the MIR
emitter migration in `src/dcc/dcc_mir.c`. It is written to be executed by a
smaller/less capable model, one item at a time, with no other context than
this file plus the repository itself. Every step that a stronger model might
otherwise infer is spelled out explicitly below. If anything in this document
conflicts with what you observe in the repository, TRUST THE REPOSITORY and
record the discrepancy in the Execution Log (do not silently guess).

This plan **supersedes and renumbers** the remaining unfinished items from
the prior plan (`mir-emitter-migration-plan.md`, items 1-50, of which 1-16
and 37 are already committed). Do not resume numbering from that document —
use ONLY the numbers in this file (1-100) going forward. The prior document
remains as historical record of what was already done; do not edit its

## Non-negotiable rules

These are hard constraints verified through real incidents in this project.
Breaking any of them has caused real bugs or wasted debugging time before.

1. **NEVER run `-UpdatePerfBaseline` and NEVER hand-edit
   `tests/perf_baselines.csv`.** Any performance regression must be
   root-cause-fixed in the code, not masked in the baseline file.
2. **NEVER stage or commit `dcc-regalloc-review.docx`** (an unrelated file
   in the repo root, always untracked). Only `git add` the specific files
   you changed.
3. **The `DCC_FORCE_STACK_CHECK=1` environment variable is read ONLY by
   `dccmake` and `runall.ps1`, NOT by the `dcc` binary itself.** When you
   manually invoke `./dcc` to compare assembly output for anything that
   touches a VLA (`mir.has_vla`) or shrinks candidate byte size, you MUST
   pass `-fstack-check` directly on the command line:
   `./dcc -stack 512 -fstack-check -I . tests/X.c -o build/Y.MAC`. Omitting
   this silently produces code without stack-check guards and makes any
   manual A/B diff meaningless. (Root cause of a multi-hour debugging
   session in the prior plan's Item 16 — see its Execution Log entry in
   `mir-emitter-migration-plan.md` for the full story.)
4. **The census tool (`scripts/mir-migration-census.py`) never builds with
   `-fstack-check`.** A change can be "census-clean" (no regression in the
   TSV) yet still flip a real selector decision and cause a cycle
   regression ONLY under `-fstack-check`, specifically in functions with
   `mir.has_vla`. For any item that shrinks generated bytes in a
   VLA-containing function, ALSO do a full assembly diff of old-vs-new
   builds compiled with `-fstack-check` directly (see Step 8 in the
   playbook below), not just the census tool.
5. **If a helper predicate/eligibility check is needed at two call sites**
   (e.g. a frame-slot-accounting pass and the actual emission-time
   decision), do NOT duplicate the expression with a "must match exactly"
   comment. Extract ONE shared function both call. A real stack-overflow
   crash bug in the prior plan's Item 16 was caused by exactly this kind
   of drift.
6. **Every item needs its own before/after census AND `runall.ps1 -Mode
   full` for every app whose census row changed**, before it can be
   considered complete. Zero tolerance for regressions of any kind
   (cycles or bytes, peep or nopeep).
7. **Write comments only to state WHY, not WHAT** — one short line, no
   multi-paragraph doc comments. Match existing `dcc_mir.c` style.
8. **Do not create new files unless the item genuinely requires it**
   (tooling items 80-82 are the only ones expected to touch files outside
   `src/dcc/dcc_mir.c`).
9. **If an item's premise does not hold** (investigation shows the
   described gap doesn't actually exist, or is already handled), record
   that finding in the Execution Log as "verified already satisfied, no
   code change" (see the prior plan's Item 15 for the precedent) and move
   to the next item. Do not force an unnecessary change.
10. **Commit and push after EVERY item**, not in batches. Use the exact git
    workflow in "Commit workflow" below.

  `DCC_MIR_REPORT=1 DCC_MIR_FUNCTION=<func> ./dcc -I . tests/<app>.c -o

  item touches VLA/byte-size-sensitive code).

  `DCC_MIR_SELECT_REPORT` (prints selector accept/fallback decisions),
  `DCC_MIR_CANDIDATES` / `DCC_MIR_GENERAL_CANDIDATES` /
  `DCC_MIR_HOME_CFG_CANDIDATES` (dump each candidate selector considered),
  `DCC_MIR_FORCE_FALLBACK_FUNCTION=<func>` (force one function through the
  legacy AST path for a true A/B diff — more reliable than a partial

  `DCC_MIR_REQUIRE_COMPLETE`, `DCC_MIR_COVERAGE`.
- Census TSV columns: `app function selector result reason
  generated_bytes captured_bytes generated_insns captured_insns blocks`.
  `result` is `accepted` or `fallback`; `selector` is one of
  `spilled-scalar-cfg` (dominant path) or `homed-scalar-cfg`.
- Key selector functions in `src/dcc/dcc_mir.c` (search for these
  function names to find the emission code for any item):
  `mir_try_emit_spilled_scalar_cfg` (the dominant selector — most items
  touch this one), `mir_try_emit_homed_scalar_cfg`,
  `mir_try_emit_scalar_dag`, `mir_try_emit_homed_scalar_dag`,
  `mir_try_emit_comparison_branch`, `mir_try_emit_countdown_loop`,
  `mir_try_emit_accumulator_loop`, `mir_try_emit_unsigned_division_loop`,
  `mir_try_emit_repeated_invariant_add_loop`, `mir_try_emit_z80` (the
  top-level dispatcher that tries each of the above in order).
  `mir_prepare_backend_slots` assigns frame slots before emission runs —
  any accounting change there must match the real emission-time decision
  (rule 5). `mir_definition`, `mir_value_use_count`, `mir_binary_only_constant`
  are reused across many items for operand provenance/eligibility checks.

## Naming convention for scratch files

Use `build/item<N>-before.tsv` / `build/item<N>-after.tsv` for each item's
census snapshots (N = this plan's item number). After an item completes
successfully, promote its `-after.tsv` to `build/mir-plan-100-before.tsv`
(the running baseline for the NEXT item's `--compare`). All of these are
under the gitignored `build/` directory — verify with `git check-ignore -v
build/item1-before.tsv` if ever unsure; never `git add` anything under
`build/`.

## Universal per-item execution playbook

Follow these steps in order for every single item in the roadmap table.
Do not skip steps. Do not start implementing before Step 3 confirms the
item's premise is real.

**Step 1 — Orient.** Read this file's Checkpoint section and the tail of
this file's own Execution Log (bottom of this document) to find the last
completed item number and the current promoted baseline path
(`build/mir-plan-100-before.tsv`, or the prior plan's
`build/mir-plan-50-before.tsv` if this is item 1 and no promotion has
happened yet). Pick the next not-started item in table order, respecting
any "depends on item N" note.

**Step 2 — Confirm the item's baseline census.** Run:
```
python3 scripts/mir-migration-census.py --output build/item<N>-before.tsv \
  --compare build/mir-plan-100-before.tsv
```
Confirm the diff is empty (0 changes) before you touch any code — this
proves you're starting from a clean, known state.

**Step 3 — Investigate and confirm the target is real.** The table's
"Target discriminator" column is a *starting hypothesis*, not a verified
fact (this is explicit for items 34-100, which are reasoned extensions of
proven families rather than pre-verified targets). For the named
app(s)/function(s):
- Run a filtered census: `python3 scripts/mir-migration-census.py --apps
  <app1,app2> --output build/item<N>-scope.tsv`.
- Grep the result for the named function and inspect its `reason` column.
- Dump its MIR IR: `DCC_MIR_REPORT=1 DCC_MIR_FUNCTION=<func> ./dcc -I .
  tests/<app>.c -o build/tmp.MAC` (add `-stack 512 -fstack-check` if the
  item or function involves a VLA or byte-size-sensitive code per rule 3).
- Read the relevant code in `src/dcc/dcc_mir.c` — search by MIR opcode
  name (`MIR_BINARY`, `MIR_STORE`, `MIR_CALL`, `MIR_VLA_ALLOC`, etc.) or by
  the selector function names listed above.
- **If the premise doesn't hold** (already handled, or the described
  pattern doesn't reproduce), stop here, log it per rule 9, and move to the
  next item — do not force a change.

**Step 4 — Implement.** Make the minimal, targeted change. Follow rules
5 and 7. Prefer extending an existing helper/selector over adding a
parallel one, unless the item is explicitly a new mechanism.

**Step 5 — Rebuild.** `sh src/dcc/build-dcc.sh`. Fix any build errors
before proceeding.

**Step 6 — Full census with regression gate.**
```
python3 scripts/mir-migration-census.py --output build/item<N>-after.tsv \
  --compare build/mir-plan-100-before.tsv --fail-on-regression
```
Confirm: which functions newly admitted (if any), which apps have any
changed row (admitted, fallback-reason changed, or byte/insn counts
changed for an already-accepted function). List every such app — that is
exactly the set you must runtime-validate next.

**Step 7 — Runtime-validate every changed app.**
```
pwsh ./scripts/runall.ps1 -Apps <comma-separated-changed-apps> -Mode full -RunTimeout 20
```
Zero regressions required (any cycle or byte metric, peep or nopeep). If a
regression appears:
- Bisect with `DCC_MIR_FORCE_FALLBACK_FUNCTION=<func>` to isolate which
  function, or use `git worktree add /tmp/dcc-before <last-good-commit>`
  to get a true old-vs-new binary comparison (do NOT use `git stash` for
  this — it does not force a rebuild and can silently compare a binary
  against itself; use a worktree instead).
- Diff the full generated assembly (not just the census numbers) for the
  regressing app, with `-fstack-check` passed directly if the function has
  `mir.has_vla` (rule 3/4).
- Fix narrowly — prefer a scoped guard (e.g. `!mir.has_vla`, or excluding
  one specific shape) over reverting the whole item.
- Repeat Steps 6-7 until clean.

**Step 8 — VLA/stack-check safety net.** If this item shrinks generated
bytes for ANY function with `mir.has_vla`, additionally: build old and new
compilers (via `git worktree`, per Step 7), compile the affected test file
with BOTH compilers using `-stack 512 -fstack-check` passed directly, and
diff the complete generated `.MAC` output. Confirm the only differences
are the ones you intended. This step exists specifically because the
census tool never builds with `-fstack-check` (rule 4) — do not skip it
just because Step 6/7 passed.

**Step 9 — Wide safety net.** For any item marked "wide safety net" in the
roadmap table (structural/CFG/cost-model items, or any item touching code
reachable by more than a handful of apps), also run:
```
pwsh ./scripts/runall.ps1 -Mode full -Extended -RunTimeout 20
```
0 failures required across all 319 apps (310 runnable) and 196 extended
tests.

**Step 10 — Promote the baseline.**
```
cp build/item<N>-after.tsv build/mir-plan-100-before.tsv
```

**Step 11 — Document.** Append one Execution Log entry to THIS file (not
the old plan) at the bottom, in the same style as the existing entries
below: what changed, why, any bugs found/fixed, the census delta, the
runtime validation results, and the new coverage fraction. If the premise
didn't hold (Step 3), write a short "verified already satisfied" entry
instead.

**Step 12 — Commit and push.** See "Commit workflow" below.
